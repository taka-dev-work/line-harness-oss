# クライアント別環境での提供 設計書

- 作成日: 2026-11-26
- 状態: ドラフト（承認待ち）
- 対象: ai-line-architect（LINE Harness fork / AI LINE CRM）

## 1. 目的と背景

AI LINE CRM を NIBEL のクライアントへサービスとして提供する。最優先はセキュリティ。

現状は「1デプロイ = 1オーナー = 1 D1」の単一テナント設計で、本番は小林さん自身の
Cloudflare アカウントに1環境だけ存在する。デプロイとシークレット投入は手元PCから手作業。
この形のままクライアントを増やすと、PC 1台・アカウント1つの侵害が全クライアントへ波及する。

## 2. 決定事項（小林さんが決めたもの）

| 項目 | 決定 |
|---|---|
| 提供モデル | クライアントごとの完全別環境（マルチテナント SaaS にはしない） |
| アカウントの持ち主 | **クライアント本人**が Cloudflare アカウントと LINE チャネルを所有し、NIBEL はメンバーとして招待される（案A） |
| 構築・更新の方式 | **非公開の運用リポジトリ + GitHub Actions**。クライアントごとの GitHub Environment、承認付きデプロイ（案2） |
| 運用リポジトリの置き場所 | **NIBEL の GitHub 組織**（Team プラン）。組織全体で二要素認証を強制する |
| クライアントの独自ドメイン | **必須**。クライアントは自社ドメイン（サブドメイン可）を自社の Cloudflare アカウントで管理する。管理用ホスト名を Cloudflare Access で保護する前提条件 |
| 承認の仕組み（2026-11-27） | GitHub の Required reviewers は Team プランの非公開リポジトリでは使えないため、**運用リポジトリの Write 権限を承認者だけに限定**し、起動＝承認とする。ワークフローも起動者がリポジトリ変数 `DEPLOY_APPROVERS` に含まれるかを確認する。承認者以外が書き込む運用になったら Enterprise Cloud か別の承認手段に移る |

## 3. ゴール / 非ゴール / アンチゴール

**ゴール**
- G1. クライアント間の完全分離：Cloudflare アカウント、Worker、D1、LINE チャネル、シークレットがすべて別
- G2. NIBEL のどの1点（PC、GitHub、1つの API トークン）が破られても、被害が1社を超えて広がらないか、少なくとも検知・失効できる
- G3. テスト済みのリリースだけを、承認を経てデプロイする。全社に同じ版のセキュリティ修正を配れる
- G4. スキーマ変更を安全に適用できる（適用履歴あり、適用前の復元点あり）
- G5. 管理画面の利用者を個人単位で発行・失効でき、操作の記録が残る
- G6. 導入（オンボーディング）と解約（オフボーディング）が手順書どおりに再現できる

**非ゴール**
- 1つの環境に複数クライアントを載せる SaaS 化
- クライアントによるセルフサインアップ、課金の自動化
- 契約書・利用規約そのものの作成（論点の一覧のみ §10）

**アンチゴール（動いても失敗とみなす状態）**
- 1つの資格情報で2社以上の環境を操作できる
- NIBEL 側（PC、運用リポジトリ、ログ）にクライアントの顧客データやアプリ用シークレットのコピーが残る
- main の未リリースコードが本番へ出る

## 4. 検討した方式（Approaches）

1. **手元PCから手順書+スクリプト**：最速だが全社の権限が1台に集まり G2 に反する。不採用
2. **非公開運用リポジトリ + GitHub Actions（採用）**：PC にシークレットが残らず、承認と記録が残る。初期構築に数日、GitHub アカウント保護が要になる
3. **クライアント自身がインストーラーで構築、NIBEL は支援のみ**：修正の適用が各社任せになり G3 に反する。不採用

## 5. 全体構成

```
[製品リポジトリ] taka-dev-work/line-harness-oss（公開）
   └─ コードのみ。アカウントID・D1 ID・ドメインを含めない
   └─ リリースタグ vX.Y.Z-nibel.N

[運用リポジトリ] <NIBEL組織>/ai-line-crm-ops（非公開・新規、Team プラン）
   ├─ clients/<slug>/client.json   … 秘密でない識別子と固定バージョン
   ├─ .github/workflows/deploy.yml … 手動起動（client, 確認用 version）
   └─ docs/runbooks/               … 導入・解約・障害・キー失効

[GitHub Environment] client-<slug>
   ├─ 必須承認者: 小林さん
   ├─ デプロイ可能ブランチ: main のみ
   └─ secret: CLOUDFLARE_API_TOKEN（そのクライアントのアカウントだけに効くトークン）

[クライアントの Cloudflare アカウント]
   ├─ Worker（管理画面アセット同梱）+ D1
   └─ アプリ用シークレット（LINE / AI / Stripe / Google）は Worker Secret にのみ存在
```

### 5.1 製品リポジトリ側の変更
- `apps/worker/wrangler.toml` から本番の `account_id` と `database_id` を削除し、プレースホルダーだけのテンプレートにする。デプロイ時に運用リポジトリの `client.json` から設定を生成する
  - 注意：既存の本番IDは公開リポジトリの履歴に残る。ID自体は秘密ではないが、§8.1 の本番環境の移行と合わせて扱う
- 既存の `.github/workflows/deploy-worker.yml`（main への push で自動デプロイ）は削除する。公開リポジトリから本番へ直接出る経路をなくす
- リリース時にタグを打つ。運用側はタグではなく**コミットSHAで固定**する（タグの付け替えで中身がすり替わるのを防ぐ）

### 5.2 `client.json`（秘密情報を含めない）
```json
{
  "slug": "acme",
  "displayName": "株式会社ACME",
  "cloudflareAccountId": "…",
  "workerName": "ai-line-crm",
  "d1DatabaseName": "ai-line-crm",
  "d1DatabaseId": "…",
  "customDomain": "line.acme.example",
  "release": { "tag": "v0.14.0-nibel.1", "commit": "<40桁SHA>" },
  "build": { "VITE_LIFF_ID": "…", "VITE_BOT_BASIC_ID": "…" },
  "adminDomain": "admin.acme.example",
  "access": { "teamDomain": "acme.cloudflareaccess.com", "aud": "<64桁のAUDタグ>" }
}
```

### 5.3 デプロイワークフロー（`deploy.yml`）
1. 手動起動。入力は `client`。クライアントに対応する Environment を使い、承認待ちで止まる
2. 製品リポジトリを `release.commit` で checkout し、指定タグがそのコミットを指すことを照合する
3. `pnpm install --frozen-lockfile`、パッケージのビルド、テスト、型チェック。失敗したら中止
4. `client.json` から wrangler 設定を生成する
5. **D1 の復元点を記録**する（Time Travel のブックマークを取得してジョブ出力に残す）
6. マイグレーションを適用する（§6）
7. `wrangler deploy`。アプリ用シークレットには触れない
8. スモークテスト：`/openapi.json` が 200（公開ルート。現状 `/api/health` のような公開ヘルスチェックは無い）、認証なしの `PUT /api/forms/<存在しないID>` が 401、`/webhook` が署名なしで拒否される
   - 追記（2026-11-27）：`/webhook` は署名が不正でも意図的に 200 を返す（`routes/webhook.ts`）ため、外部からは拒否を確認できない。スモークテストはこの項目を持たない
9. 失敗したら直前のバージョンへロールバックする手順をジョブ出力で案内する（自動ロールバックはしない）

### 5.4 Cloudflare API トークン
- クライアントが NIBEL のメンバーを自社アカウントへ招待する
- NIBEL は**そのアカウント専用のトークン**を作る。権限は Workers Scripts:Edit、D1:Edit、必要なら Workers Routes / カスタムドメインのみ
- 有効期限を付け（例：180日）、期限が来たら作り直す
- トークンは GitHub Environment の secret にだけ置く。PC に保存しない

### 5.5 アプリ用シークレット
- LINE、AI プロバイダー、Stripe、Google の各シークレットは **Worker Secret にのみ**存在させる。GitHub にも運用リポジトリにも置かない
- 投入は導入時の1回だけ。次のどちらかで行う
  - クライアント自身が Cloudflare ダッシュボードで入力する（推奨）
  - NIBEL 担当者が画面共有のもとで `wrangler secret put` を対話入力する。ファイル経由（`sync-worker-secrets-from-env.mjs`）は使わない
- ローテーション手順を runbook に用意する

## 6. スキーマ移行

現状の `pnpm db:migrate` は `schema.sql` 全体を本番へ実行する方式で、適用履歴が残らない。

- `wrangler d1 migrations` 方式（`migrations_dir`＋適用済みテーブル）へ切り替える
- 既存の `packages/db/migrations/001〜031` と `schema.sql` の差分を検証し、新規環境用の初期化と既存環境用の追加分を整理する
- 既存の本番 D1 には「ここまで適用済み」という基準点を記録してから切り替える
- 破壊的な変更（DROP、型変更）は「追加 → 移行 → 削除」の2リリースに分ける

## 7. 管理画面の認証強化

現状は `staff_members` に owner、admin、staff の役割と個人キーがあるが、キーが**平文で D1 に保存**され、操作記録はない。

- スタッフキーは SHA-256 ハッシュで保存し、平文は発行時に1回だけ表示する（キーは高エントロピーの乱数なので、ソルトは不要と判断）
- 環境変数 `API_KEY`（オーナーキー）は導入直後の初期設定専用とする。最初のオーナースタッフを作った後は削除する運用にする
- キーの比較は定数時間で行う
- **監査ログ**：認証が必要な API への変更系リクエスト（POST/PUT/PATCH/DELETE）について、誰が・いつ・どのルートを・結果コードを記録する。本文は記録しない（個人情報を増やさない）。保存期間は既定で1年
- Cloudflare Access（メールのワンタイムコード、または SSO）を管理画面の前段に置く。管理画面（`apps/web/out`）は公開エンドポイントと同じ Worker から配信されているため、**管理用ホスト名（例：`admin.<クライアントのドメイン>`）を分け**、そのホスト名だけを Access で保護する（ビルダー判断として採用）
- Worker 側では、スタッフ認証が必要な API について、`ACCESS_AUD` が設定されている場合は `Cf-Access-Jwt-Assertion` を検証する。これで API Key が漏れても、Access を通らない限り管理 API は使えない。LIFF、webhook、フォーム送信などの公開エンドポイントは対象外にする

## 8. 運用手順（runbook）

### 8.1 既存本番（takanorixai）の扱い
- 最初の「クライアント0号」として運用リポジトリに載せ、全手順をここで試す
- 実在の友だちデータの有無を確認してから進める

### 8.2 導入（オンボーディング）
1. クライアントが Cloudflare アカウントを作り、二要素認証を有効にし、NIBEL を招待する
   - 使うドメイン（またはサブドメイン）をクライアントの Cloudflare で管理する状態にする（必須。できなければ導入を開始しない）
2. クライアントが LINE 公式アカウントと Messaging API / LINE Login チャネルを作り、NIBEL を権限付きで追加する
3. NIBEL が D1 を作成し、`client.json` を作成して運用リポジトリにプルリクエストを出す
4. Environment を作り、承認者を設定し、トークンを登録する
5. アプリ用シークレットを投入する（§5.5）
6. 初回デプロイと初期化を行い、オーナースタッフを作成してから `API_KEY` を削除する
7. Webhook URL を LINE に設定し、実機で確認する（チェックリストは既存の `ai-line-crm-line-test-checklist.md`）

### 8.3 解約（オフボーディング）
1. 必要ならデータをエクスポートしてクライアントに渡す（NIBEL 側には残さない）
2. NIBEL のトークンを失効させ、Environment を削除し、`client.json` を archive へ移す
3. クライアントが NIBEL のメンバー権限と LINE チャネルの権限を外す
4. 完了をクライアントと書面で確認する

### 8.4 インシデント時
- 疑わしいトークンやキーを失効させる：該当社の Cloudflare トークン、スタッフキー、LINE チャネルアクセストークン
- D1 の Time Travel で影響範囲を確認する
- 連絡は §10 で決めた期限と経路で行う

## 9. GitHub 側の前提
- 運用リポジトリにアクセスできる全員に二要素認証を必須にする
- Environment の承認を必須にし、自己承認を禁止するかは人数次第（1人運用の間は許容）
- サードパーティの Actions はコミットSHAで固定する
- `permissions:` を最小化する（`contents: read`）

## 10. 人が決める論点（契約・個人情報）

設計では決めない。ここでは一覧にするだけ。
- 個人情報保護法上の位置づけ：NIBEL はクライアントから委託を受ける立場か
- 再委託先と外国にある第三者への提供（Cloudflare、LINE、OpenAI、Anthropic、Google）の説明と同意
- 侵害時の通知期限と連絡経路
- AI API キーの持ち主と費用負担
- サポート範囲、稼働率の約束、セキュリティ修正の適用期限
- 解約時のデータ返却・削除の期限

## 11. 実装の順序（案）
1. 製品リポジトリ：wrangler テンプレート化、自動デプロイの削除、マイグレーション方式の切り替え
2. 運用リポジトリとデプロイワークフロー。クライアント0号で検証
3. 認証強化：キーのハッシュ化、監査ログ、Cloudflare Access
4. runbook の整備と1社目の導入

## 12. 未決事項
- AI API キーの持ち主と費用負担（§10）。どちらでもシークレットの置き場所（Worker Secret）は変わらないため、実装は先に進められる
- 既存本番（クライアント0号）に実在の顧客データがあるか。あれば §8.1 の移行で、マイグレーションの基準点を記録する前に D1 のエクスポートを取る

## 13. ビルダーに任せる点
- `client.json` のスキーマ検証方法
- スモークテストの細部
- 監査ログのテーブル設計とインデックス
- `schema.sql` とマイグレーションの差分を整理する具体的な手順
